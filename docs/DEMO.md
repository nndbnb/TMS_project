# Демонстрация ЛР1

Это приложение к [отчёту](REPORT_LR1.md), а не его часть. Нужен Python 3.11+.
Все команды выполняются из корня проекта; при необходимости использовать `python3` или `py -3.11`.

## 1. Обычная работа

```bash
python -m warehouse --output output/baseline
```

Показать три робота с разной грузоподъёмностью, семь заданий, их исполнителей и моменты
доставки/завершения. В итогах должно быть `finished: true`, `tasks_completed: 7`,
`tasks_unassignable: 0`, `tasks_unfinished: 0`.

Объяснить: диспетчер выбирает подходящего исполнителя с минимальным избытком грузоподъёмности.
Робот принимает задание только после собственной проверки. Грузоподъёмный робот
нужен для заданий массы 6–7, которые R1 и R2 выполнить не могут.

## 2. Пошаговый обмен сообщениями

```bash
python -m warehouse --step --output output/step
```

Нажать Enter несколько раз. На такте 0 роботы отправляют `STATUS`.
На такте 1 диспетчер получает статусы и отправляет назначения.
На такте 2 роботы получают назначения, отправляют `ACCEPT` и начинают движение.
На такте 3 диспетчер получает подтверждения.

Ввести `q` для остановки и сохранения промежуточной трассы. Код выхода 2 в таком случае ожидаем.
Открыть `output/step/trace.jsonl`: `message_sent` содержит полную оболочку,
`message_delivered` ссылается на тот же `sequence`. Снимки `snapshot` показывают состояние
всех роботов, заданий и зарядной очереди после каждого такта.

## 3. Ограниченный ресурс

```bash
python -m warehouse --scenario scenarios/charger_queue.json --verbose --output output/charger_queue
```

У трёх роботов по 12 единиц энергии; доступно одно зарядное место со скоростью 1.
Показать состояния `waiting_charge` и `charging`, а в трассе — `charger_owners` и `charger_queue`.
Одновременно владельцем места бывает не более одного робота.
Суммарное ожидание здесь — 31 робототакт: ожидания разных роботов складываются,
поэтому это не длительность единственной очереди на временной оси.

Правило FIFO задаёт исходное поведение. Переговоры и сравнение правил очереди — будущая ЛР3.

## 4. Невыполнимые задания

```bash
python -m warehouse --scenario scenarios/infeasible.json --output output/infeasible
```

Показать `valid` со статусом `completed`, `too_heavy` и `too_far` со статусом `unassignable`.
Второе задание превышает грузоподъёмность, третье — энергетический бюджет полного рейса.
Итог: выполнено 1 из 3, невыполнимых 2, незавершённых 0.
`finished: true` означает завершение обработки сценария, а не успешную доставку всех грузов.

## 5. Поздние задания и срок

```bash
python -m warehouse --scenario scenarios/delayed.json --output output/delayed
```

До такта 10 перевозки не начинаются; задание `late` поступает только на такте 45.
У `urgent` мягкий срок 12. Показать положительное `delivery_tardiness`:
приоритет меняет порядок выбора, но не гарантирует соблюдение срока.

## 6. Проверки

```bash
python -m unittest discover -s tests -v
```

Ожидается `Ran 23 tests` и `OK`.

Основные проверяемые свойства: единственность назначения и доставки, маршрут до базы,
точная граница энергии с резервом, вместимость зарядки, FIFO, приоритеты, задержка сообщений,
локальный отказ и повторная публикация готовности, защита реестра от результата чужого робота,
ограничение числа тактов, экспорт и повторяемость.

Итоги получены реальными прогонами прототипа на Python 3.12.14.
Полные JSON-итоги сохранены в [examples/](../examples/).

| Сценарий | Тактов симуляции | Выполнено | Невыполнимо | Сообщений | Пройдено клеток | Ожидание зарядки |
|---|---:|---:|---:|---:|---:|---:|
| baseline | 80 | 7 | 0 | 80 | 112 | 5 |
| charger_queue | 45 | 4 | 0 | 43 | 30 | 31 |
| delayed | 64 | 3 | 0 | 35 | 34 | 1 |
| infeasible | 14 | 1 | 2 | 11 | 6 | 0 |

Это контрольные запуски одного алгоритма, а не экспериментальное сравнение механизмов.

## Значение метрик

| Поле | Определение |
|---|---|
| `ticks` | Число выполненных тактов; первый имеет номер 0. Включает финальную зарядку и доставку последних статусов |
| `mission_makespan` | Такт получения последнего `COMPLETE`, отсчитанный от общего начала t=0; `null`, если завершённых рейсов нет |
| `assigned_at` | Такт отправки `ASSIGN`; при отказе до следующего назначения сбрасывается |
| `delivered_at` | Такт разгрузки груза в точке назначения |
| `completed_at` | Такт получения диспетчером `COMPLETE` после возвращения робота |
| `delivery_tardiness` | `max(0, delivered_at - deadline)`; `null`, если срока или доставки нет |
| `messages_sent` | Все сообщения шины, включая начальные/последующие статусы и подтверждения |
| `messages_by_kind` | Число отправленных сообщений каждого типа |
| `distance` | Сумма перемещений всех роботов в клетках, включая возвращение |
| `charge_wait_ticks` | Сумма тактов неуспешного ожидания места у всех роботов; переход к зарядке не включён |

Время — условные такты модели, не секунды работы компьютера.
`mission_makespan` не является максимальным временем обслуживания отдельного задания.
Стоимость координации в денежном выражении в ЛР1 не рассчитывается.

## Повторный запуск и собственный сценарий

```bash
python -m warehouse --scenario output/baseline/scenario.json --output output/replay
```

При одинаковых входных данных и версии программы итоги и события совпадают.
В JSON сценария можно менять размеры склада, базу, число зарядных мест, скорость зарядки,
резерв энергии, характеристики роботов и задания. Координаты должны лежать внутри склада,
идентификаторы быть уникальными, массы и ёмкости — положительными целыми числами.
Пример полного формата — `scenarios/baseline.json`.

Для искусственно короткого прогона:

```bash
python -m warehouse --max-ticks 3 --output output/limited
```

Ожидается код выхода 2, `finished: false` и незавершённые задания.
Это демонстрация корректного ограничения моделирования, а не диверсионное испытание ЛР4.
